# Dashboard design: brief, screens, decisions

Owner: **Zach**. Branch: `design/arena-ui`. Sandbox: `apps/web/src/design/` (components, fixtures, the flow and its replay engine) and `apps/web/src/app/design/` (routes). Nothing in the sandbox talks to the runner; every screen renders recorded reports from `apps/web/src/design/fixtures/`. The point of this phase is to settle the interface and the experience before wiring. Wiring is a later step and is described at the end.

The sandbox rules are in [`apps/web/src/design/README.md`](../apps/web/src/design/README.md). The intent behind the product is in [SPEC.md](./SPEC.md); the flow the screens follow is the subsection _The user flow — URL first, repository second_ in section 2.

## The direction (2026-10-18, second pass)

The first pass was a dense one-screen Arena. Zach's direction replaced it: give the user only what they need, one step at a time, in a light palette with one accent, with diagrams and light illustration carrying the process. The result is the four-step flow at `/design/flow`:

| Step | The user                          | The screen                                                                                                                                                                                                               |
| ---- | --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1    | Pastes a store URL. Nothing else. | **Store.** One field, one button, then the derived mission ("we will try to buy a black hoodie, size M, under $60") and one more button                                                                                  |
| 2    | Watches                           | **Scan.** Four lanes, one per agent: what it is doing in plain words, where it is on the purchase path, its latest viewport, cost ticking up, checkpoint ticks filling in when it verifies. Then one line and one button |
| 3    | Reads the problems                | **Findings.** One card per problem, evidence first: what we saw, who it affects, what it cost, the likely cause labelled as a hypothesis, the computed recommendation. Then one action: connect GitHub                   |
| 4    | Connects the repository           | **Fixes.** A short reading beat over the repository's files, then one card per problem with the patch, folded, and Copy patch. The flow ends here                                                                        |

A persistent stepper (Store, Scan, Findings, Fixes) sits in a minimal header; the line between nodes fills with the accent as steps complete, the active node breathes while work runs, and completed nodes are clickable to look back. Nothing from a later step shows before its time, and nothing advances without a click.

Open it with `pnpm --filter @agentproof/web dev` and `http://localhost:3000/design/flow`. `?step=1..4` opens a step directly, `?speed=0.5|1|2|4` and `?t=<ms>|end` drive the scan replay, and a dev-only pill in the corner does the same by click.

## What the dashboard has to do

From [SPEC.md section 10](./SPEC.md#10-mvp-scope-for-24-hours) and the dashboard row in [WORKPLAN.md](./WORKPLAN.md):

- Take a storefront URL and a natural-language mission.
- Let the user pick agents, then show one panel per run with the latest screenshot and the steps so far, live.
- Show the checkpoint matrix: checkpoints down, agents across, pass / fail / not run.
- Show the attribution line (which agent passed, which failed, what that says about the store) and the cost per agent.
- Link to the agent and mission reports.
- Show each issue with its evidence, the labelled hypothesis, the connect-repository ask, the diff and Apply.
- Show the rematch: the same matrix before and after the repair.
- Keep the existing Gamma flow (today's `apps/web/src/app/page.tsx`) working underneath until the new screens replace it.

In the flow: the mission is derived rather than typed (editable behind "Change"); all four agents run, there is no picker; the matrix is a collapsed disclosure under the scan summary; attribution and cost live inside each problem card; the report is a download; Apply and the rematch are not in the flow (they stay on the Gamma page).

The demo is a three-minute recorded video at desktop width. Design for 1440 by 900 first. Phone layouts are not required.

## Principles the design must respect

These come from the project rules and are not open for debate in the design pass.

- **Verdicts are code.** Pass, fail and budget math come from the verifier. The UI never softens or reinterprets them. Anything written by the model is shown as a narrative or a hypothesis and labelled as such.
- **Cost is a first-class number.** Every agent shows what it cost. The thesis is that the cheapest agent (Alpha, text only) should pass. When Alpha fails and a dearer agent passes, the screen says so in one line.
- **Evidence before explanation.** Observed facts (which variant the page showed, which the cart returned) come before any hypothesis.
- **The repository is asked for on the issue, not at launch.** Launch takes a URL. The connect-repository ask lives under the findings.
- **Agents never pay.** Checkout review is the last checkpoint. The scan subtitle and the derived mission both say the shoppers stop before paying.

## Visual system

- **Palette.** Scoped to the flow by `data-theme="light"` on its root; the dark tokens on `:root` stay for the Gamma page and the first-pass sandbox screens. Neutrals: `#ffffff` background, `#15181e` ink, `#5b6170` muted, `#f6f7f9` and `#eceef2` panels, `#e2e5ea` lines, `#b9bfc9` input borders. One accent for progress, the active step, primary buttons and diff additions: `#2563eb`. The only other colour, for failures and diff removals: `#dc2626`. Pass states are ink with a check mark, never green; `--pass` and `--warn` are redefined to neutrals under the light theme so the reused chips go monotone with no code change. Validated with the dataviz validator against white: every check passes; the accent and the red sit 29.9 Delta E apart under protanopia and both clear 3:1 on the surface.
- **Type.** System sans; 28 px semibold titles, 15 px body, 13 px meta, tabular numbers.
- **Motion** (`motion/react`, client components only, inside `MotionConfig reducedMotion="user"`). Step transitions fade and rise 12 px over 220 ms; the stepper's active pill slides between nodes; the mission card rises in; lane markers spring along the track; viewports crossfade; checkpoint ticks scale in on the burst; findings and fix cards stagger 80 ms; the connect form expands; the reading bar and counter run over 2.2 s; the illustrations draw themselves in over 700 ms. CSS only: the running pulse, the shimmer before the first frame, hover and focus. Replay pacing is content and survives reduced motion.
- **Illustrations and icons.** Four inline SVG marks (storefront, lanes to a cart with a magnifier, a card with a flagged chip, a document with a removed and an added line) in `flow/illustrations.tsx`, 64 by 64, paths only, 1.5 px, `currentColor`. Eight glyphs in `flow/icons.tsx`. No icon library.

## Architecture of the sandbox flow

- `apps/web/src/app/design/flow/page.tsx` is the server boundary and the only importer of the fixtures. It builds the replay script, maps every frame path to its URL and passes plain JSON to the client, so the server render and the first client render agree and `?step=3` paints step three with no flash.
- `apps/web/src/design/flow/flow.tsx` is the client root: the flow reducer (`flow-machine.ts`, pure, tested), the replay hook, the step switch, the motion wrapper, and the two sandbox beats (700 ms to derive the mission, 2.2 s to read the code) that become real calls at wiring.
- `apps/web/src/design/replay/` turns the four recorded run reports into real `RunEvent`s on a compressed clock (`script.ts`, pure, tested), folds events into one `LaneState` per agent (`reduce.ts`, pure, tested), and plays them on a timer (`use-replay.ts`). At wiring, the runner's event stream feeds the same reducer and the Scan screen does not change.
- Every step component is props-only. `format.ts` holds the plain-language helpers (`describeMission`, `plainAction`, `stageOf`, `costLine`, `summarize`).

## Data the screens render

Recorded on 2026-10-18 through the runner; details in [RESULTS.md](./RESULTS.md). Bug A on the bugged store, four agents: Alpha fails _Correct size identified_ (no size control in the accessibility tree) and ends with size S in the cart; Beta and Sigma pass; Gamma fails _Catalog variant ID resolves_ through the cart API. Alpha and Beta cost a quarter of a cent each, Sigma about five cents, Gamma nothing.

Composed for the flow, parsed with the shared schemas and tested: two issues whose `observed` text and evidence ids are verbatim from the recorded checkpoints (the Gamma hypothesis fields are hand-written and flagged), two repairs whose diffs are the reference patches, and one hand-written repository connection with the real storefront file list.

## Open questions

- Scan density: the step count and cost on each lane, or only the plain-words action?
- Findings: should the two problems be ranked, with the cheapest-shopper failure first?
- Fixes: which delivery mode the demo uses, now that the code-fix agent exists: `diff` (Copy patch and a patch download, no credential) or `pull_request` (a draft pull request opened by the GitHub App, linked from the card)? And whether the card shows the opt-in rematch as one line of proof ("Alpha passes on the patched store") without reopening the before/after table.
- The stepper's completed nodes let the user look back; should a step they revisit be read-only?

## Wiring plan (later, not in this phase)

- Step 1 needs a URL-only mission: `POST /missions` accepting a missing prompt and deriving one from the store, or a new endpoint. Until then the real page can take the prompt behind "Change".
- Step 2 needs `POST /missions/:id/runs` with all four kinds, then one `GET /runs/:id/events` subscription per run into the same reducer. Load `GET /runs/:id` first, since the stream does not replay earlier events.
- Step 3 needs diagnose per failed run (today) or per mission (better). The repository connection is still per run (`POST /runs/:id/repository`, localhost only), but the gate is now any failed run with a failed checkpoint rather than Gamma only, so the page connects the same repository to each failed run (Alpha and Gamma here) until the backend grows a per-mission connection. The form's three inputs are unchanged (`ConnectRepositoryRequest`; the token pattern widened). When `GET /github/app` reports `configured`, hide the token field: the app installation clones private repositories and opens pull requests, and `RepositoryConnection.accessVia` says which credential was used, worth one line on the Fixes step.
- Step 4 is the code-fix agent, merged 2026-10-18 (PRs #6 and #7; design in [CODEFIX.md](./CODEFIX.md), live results in [CODEFIX-RESULTS.md](./CODEFIX-RESULTS.md)). The sandbox shows a `Repair` per issue; the backend produces one `CodeFix` record per failed run with a connected repository. What the step wires to:
  - Start: `POST /runs/:id/codefix` with `{ mode: 'diff' | 'branch' | 'pull_request', consent: true, storeRoot?, token?, typecheck?, review?, rematch?, maxAttempts? }` returns 202 with the record in `running`. `diff` needs no credential; `branch` and `pull_request` need the GitHub App or a fine-grained token. The web client already has `startCodeFix`, `getCodeFix`, `listCodeFixes`, `subscribeCodeFix`, `codeFixPatchUrl`, `codeFixMarkdownUrl` and `getGitHubApp`.
  - The reading beat becomes real: `GET /codefix/:id/events` streams `stage` events through `collect`, `localize`, `propose`, `validate`, `review`, `rematch` (opt-in), `deliver` and `done`, plus `log` lines. The invented file counter is replaced by `localization[]` from `GET /codefix/:id`: the ranked files with `path`, `matchedTerms` and `included`, which is what "Reading your code" should show.
  - Each fix card renders `attempts[finalAttempt]`: `proposal.diagnosis` (`title`, `inferredCause`, `confidence`) labelled as a hypothesis, `proposal.summary` labelled as the model's summary, the code-written `diff` and `files` in the existing `DiffView`, `validation.checks` as a check table (paths in scope, no dependency changes, size within bounds, applies cleanly, content policy, typecheck, rematch), `review` as a second opinion with its verdict, never as a status, and `usage` for the cost line. From the sandbox shape: `Repair.summary` is `proposal.summary`, `Repair.diff` and `Repair.files` are the final attempt's, `Repair.status` becomes `status` plus `delivery.status`. The record's `input.observed` and `attributionCategory` are the same facts the Findings card shows, so the two steps agree by construction.
  - Delivery settles the "Copy patch" question: in `diff` mode the card keeps Copy patch and links `GET /codefix/:id/patch.diff`; in `branch` mode `delivery.compareUrl` is GitHub's prefilled "open a pull request" page; in `pull_request` mode `delivery.pullRequestUrl` is a draft pull request, always a draft, never merged. The flow still ends at suggested changes.
  - `rematch: true` reruns the failing agent against the patched store and fills `rematch.comparison`. The flow does not show the before/after table; one line of proof on the card is cheap if wanted (open question above).
  - Fixtures: once a fix has run through the runner on the demo repository, record its `CodeFix` JSON under `apps/web/src/design/fixtures/` and drop the hand-written repair fixtures and the Gamma hypothesis.
  - Still missing for this flow: a fix per mission rather than per run (two failed runs mean two requests and two records today), and the URL-only mission from Step 1.
- The route-group layout split (flow vs Gamma page) is the right long-term shape for the header; do it at wiring, not on this branch.
- Delete the sandbox beats in `flow.tsx`, the dev controls, and `?step`/`?t` handling when the real calls land.
